# TypeScript Reflection

TypeScript has changed how I think about software development in a number of ways. It's essentially Java's philosophy but adapted for app and web development. Typescript, like Java, enforces type safety, object-oriented programming principles, and compile-time checking. However, instead of running on the JVM, it transpiles to JavaScript and gives you access to the entire web development system, which is what makes it so interesting to me. Typescript allows you to be pragmatic with your tools in a way no other language can. 

Mastering TypeScript is actively building the foundation for my career in web and application development. These lessons are not specific to TypeScript, and will transfer to whatever language or technology I decide to learn in the future. Whether I'm building applications, working in big tech, the lessons learned in this class will carry on with me forever. Things like catching errors and writing readable code is an investment in myself in order to become the best software developer I can be.

When comparing TypeScript to alternatives like C++ or Python, the advantages of TypeScript separate this language from the rest. C++ is fast and powerful, but does not work well for web development because it requires compilation and does not connect to browsers, as it works primarily in operating systems. Python is great for backend work and data science, but it requires frameworks like Django to work in the web, which add extra layers that aren't needed in TypeScript. TypeScript compiles directly to JavaScript that runs in every browser, and has access to the DOM and web APIs without translation. It can run on both client and server through Node.js, so you can build full stck applications with only one language. TypeScript catches bugs before runtime, whereas Python catches them at runtime. Typescript is also more lightweight than C++, and you don't need anything inbetween the code and the browser.

# Athletic Software Engineering

Our class runs on an "Athletic Software Engineering" program, in which programmers should constantly be solving problems and coding everyday, often under strict time restraints. However, I find problem with this. Speed and practice matter, but it can easily become ineffective reps. When you're always programming, you don't really have time to absorb what you're learning, or look back at what you've worked on previously and pick up on anything. You're always onto the next. The pressure to always be productive can actually work against learning. 

This issue is still partially prevalent in the modern software engineering industry today. With things like crunch culture still around, quality is often superceded for volume and outcome. Real exellence in regards to software engineering means rethinking what productivity actually means. It's not about how much you code or how many problems you solve, but rather it's about understanding what you're doing and building systems that actually work well. As I build my career in web development, I want to be known for the quality of what I build, not how fast I can code.

This course would improve drastically if we cut the volume of assignments in half and focused on curated, quality assignments that teach concepts in a less hasty manner.
